## 2. Risques détectés

### P0 — bloquant / dangereux

1. **Script de test qui tape la production.**
   `scripts/test_pawapay.ts` charge `.env.local` et appelle `https://api.pawapay.io` avec le **token de production**.
   → Risques : mouvements d'argent réels, lignes de test dans le ledger de prod, fuite du token dans les logs/CI, rate-limiting du merchant.
   → Correctif : environnement *sandbox* dédié (`PAWAPAY_BASE_URL` / `PAWAPAY_TOKEN` distincts), guard qui refuse l'exécution si le token prod est détecté ou si `NODE_ENV=production`, masquage systématique du MSISDN et du token dans les sorties.

2. **Aucune validation de l'environnement au démarrage.**
   Le premier build prod a échoué parce que `PAWAPAY_BASE_URL` manquait — alors que la variable existait déjà côté Vercel. C'est le symptôme classique d'une config non typée/non validée : on le découvre au build, pas au démarrage.
   → Correctif : schéma d'env validé (Zod ou `t3-env`) chargé avant l'init du client, échec explicite avec message actionnable, `.env.example` à jour, checklist des variables Vercel versionnée.

3. **Double source de vérité sur les crédits.**
   Ancien modèle (`payments.campaign_id` + `credit_campaign_quota`) et nouveau (`account_credit_balances` + `account_credit_ledger`) cohabitent. Sans backfill ni verrou, les deux vont diverger : un utilisateur verra un solde différent selon le chemin de code emprunté.
   → Correctif : script de backfill idempotent (1 ligne legacy → 1 écriture ledger), puis ancien modèle en lecture seule, puis contrôle de cohérence `SUM(ledger) == balance`.

4. **Concurrence / idempotence du ledger non prouvée.**
   PawaPay peut renvoyer le même callback plusieurs fois, en parallèle. Si le solde est recalculé ou incrémenté hors transaction, on obtient des doublons de crédits.
   → Correctif : ledger append-only, contrainte d'unicité sur la clé d'idempotence (`paymentId` + type d'événement), mise à jour du solde dans la **même transaction** (ou verrou advisory par compte), upsert plutôt qu'insert.

5. **Numérotation et immuabilité des factures.**
   Le journal parle de « modèle immuable » mais rien n'indique une numérotation séquentielle **sans trou** (exigence fiscale dans la plupart des juridictions) ni un verrouillage en écriture après émission.
   → Correctif : séquence Postgres ou compteur verrouillé (`SELECT ... FOR UPDATE`), `UNIQUE(invoice_number)`, trigger refusant la modification des champs figés (montant, devise, identité, lignes) après émission, et **avoir** (credit note) pour toute correction.

6. **Contrôle d'accès sur les factures (IDOR).**
   Le journal vérifie seulement que `/api/billing/summary` renvoie 401 en anonyme. Rien ne prouve que la facture d'un compte A est inaccessible au compte B.
   → Correctif : filtrage par `user/account_id` dans la requête, renvoi 404 (pas 403) si la facture n'appartient pas à l'appelant, et test d'accès croisé explicite.

### P1 — important

7. **RLS : seules des policies SELECT sont mentionnées.**
   Il faut vérifier qu'**aucune** policy n'autorise `INSERT`/`UPDATE` client sur `account_credit_ledger`, `account_credit_balances`, `invoices`. Ces écritures doivent être exclusivement serveur (service-role, webhook).
   → Correctif : audit `pg_policies`, suppression de toute policy `FOR ALL` sur ces tables, ajout d'un test qui tente une insertion avec une clé anon et échoue.

8. **Signature du webhook : vérifier le corps brut.**
   « Webhook signé » est rassurant, mais une signature calculée sur un JSON re-sérialisé est invalide — bug classique. À contrôler : lecture du raw body, comparaison à temps constant, fenêtre anti-replay sur le timestamp, réponse 200 rapide avec traitement asynchrone.

9. **`country` codé en dur à `'BFA'`.**
   Dès le premier utilisateur hors Burkina Faso, le paiement échouera silencieusement.
   → Correctif : source unique de vérité (constante de config ou champ sur le compte), devise explicite et cohérente avec le pays.

10. **Montants en virgule flottante.**
    À vérifier : les montants doivent être des **entiers** dans la plus petite unité (XOF n'a pas de décimales, mais le réflexe doit être POSIX). Aucun `number` flottant dans le ledger, les factures ou les payloads PawaPay.

11. **Zéro nouveau test pour le code de facturation.**
    Les 39/39 et 8/8 sont des contrôles préexistants. Aucun test cité pour : idempotence webhook, concurrence ledger, numérotation facture, RLS, IDOR. « Le code compile » n'est pas « le code est testé ».

12. **Déploiement direct en production depuis `master`.**
    Pas de mention de preview/staging, pas de plan de rollback pour la migration `0021`, pas de sauvegarde citée.
    → Correctif : preview Vercel systématique, migration réversible (ou au minimum un `down` documenté), procédure de rollback écrite.

13. **Pas d'observabilité sur les échecs.**
    Rien sur : webhook reçu mais non traité, échec de réconciliation `/check`, échec de génération de facture. Sans ça, un paiement encaissé sans crédits attribués ne remonte pas.
    → Correctif : table d'audit/dead-letter (hash du payload, statut, erreur, tentatives), alerte, script de réconciliation manuelle.

### P2 — souhaitable

14. **Parcours anonyme non couvert.** `/tarifs` redirige vers le dashboard : que se passe-t-il pour un visiteur non connecté ? Formule, durée et `returnTo` survivent-ils à l'inscription *et* à l'onboarding ? À tester explicitement.
15. **Pas de PDF.** « Facture téléchargeable » implique génération PDF (et idéalement archivage en Storage + URL signée + envoi par e-mail).
16. **Pas de remboursement / avoir.** Tout système de facturation finit par en avoir besoin : prévoir dès maintenant des écritures négatives au ledger et un type `credit_note`.
17. **TVA / mentions légales** : à cadrer avant la première facture émise (identité de l'émetteur, numéro de TVA, mentions obligatoires).

## 3. Propositions d'amélioration (priorisées)

### Immédiat (cette semaine)
- Sandbox pour les tests PawaPay + guard anti-token-prod + masquage des données sensibles. **Rotation du token de production** : il a été utilisé dans un script local.
- Schéma d'env validé au démarrage + `.env.example` + checklist Vercel versionnée.
- Unicité/idempotence sur le ledger et les webhooks ; solde mis à jour dans la même transaction.
- Backfill idempotent legacy → ledger + contrôle de cohérence.
- Numérotation séquentielle + immuabilité des factures.
- Tests d'accès croisé (IDOR) sur `/api/invoices` et `/dashboard/factures/[id]`.

### Court terme
- Audit RLS complet (policies listées, `FOR ALL` supprimées, test d'insertion anon).
- Table d'audit webhook + alerting + script de réconciliation.
- Preview Vercel obligatoire avant prod ; procédure de rollback documentée pour `0021`.
- Pays/devise dans une config centralisée, plus de `'BFA'` codé en dur.

### Moyen terme
- Génération PDF des factures + archivage Storage + URL signée + envoi e-mail.
- Avoirs/remboursements (écritures négatives + `credit_note`).
- Cadrage TVA / mentions légales.
- Single source of truth : décommissionner l'ancien modèle de crédits une fois le backfill validé.

### Amélioration du journal lui-même
Le journal est clair, mais il mélange trois niveaux (décisions, exécution, vérification) et ne dit pas ce qu'il **reste** à faire. Ajouter systématiquement :

```markdown
## Journal — AAAA-MM-JJ

### Contexte / objectif du jour
### Fait
### Décisions (et pourquoi)
### Risques ouverts / dette contractée   <- le plus important
### Vérifications exécutées (commande + résultat réel)
### Prochaines étapes (TODO priorisé)
### Liens (commit, PR, preview Vercel, ticket)
```

Règles : une section « risques ouverts » obligatoire ; distinguer « compile » de « testé » ; toute migration Appliquée doit avoir son rollback documenté ; citer les résultats réels, pas « conforme ».
